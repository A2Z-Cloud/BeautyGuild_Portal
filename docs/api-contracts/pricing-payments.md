# Catalogue-driven Stripe checkout

Follows V1 (`beauty-guild-catalyst`): the portal function creates the Stripe Checkout Session and holds the Stripe key. **Creator owns the Stripe webhook and everything after payment** (marking Deals Active, invoices, payment and add-on records). This function has no webhook.

## How it works
- `src/catalogue.js` lists ITEMS (each points at a Stripe price by its **lookup key**, which is the price list code, for example `ACC-STD` or `MEM-ASSOC-Y`) and SERVICES (who may pay, which items apply, the metadata Creator expects).
- Books holds the price list and every item's SKU is the same code. The portal stores no amounts and no price IDs: it asks Stripe for the active price with that lookup key and reads the live amount (must be active, GBP, with the interval the catalogue expects). To change a price, create the new Stripe price with the same lookup key (move the key over with `transfer_lookup_key`); no deployment or environment change is needed. A code with no active price makes the item `ITEM_NOT_AVAILABLE`.
- `GET /portal/checkout/quote?service=&recordId=` returns a server-built summary. `POST /portal/checkout` creates the session and returns `checkoutUrl`. Amounts from the browser are ignored.
- Every request needs a signed-in user whose verified email matches exactly one CRM Contact, and the record must belong to that Contact.
- Metadata keys match V1 (`type`, `accreditation_id`, `contact_id`, `membership_deal_id`, `product_amount`, ...) so Creator keeps working.
- Open sessions for an accreditation are reused (`Stripe_Checkout_Session_ID`); paid ones return `alreadyPaid`. Accreditation sessions write `Stripe_Checkout_Session_ID` and `Payment_Status = Payment Processing` back to the CRM, as V1 does.
- Only `sk_test_` keys are accepted until live use is agreed.

## Services now
`insurance` (standalone), `accreditation` (bundle price when the Contact has no current membership, international price rule as V1), `additional_venue`, `membership_addon`, and `membership` (new, renewal, upgrade).

### Membership purchase
- Levels `associate`, `full_non_salon`, `full_salon` (international is refused: priced individually). Branches `beauty|holistic|nails|hair`; additional branches and add-ons optional. Annual or monthly.
- Subscription mode: everything that renews is a yearly subscription line (the membership, extra branches, and any insurance premiums, IPT and employee fees); the joining fee (new members only) and add-ons are one-off lines on the first invoice. An extra branch is an inline yearly price at the live `MEM-BRANCH` amount. Stripe prices must have the interval the catalogue expects (year/month, count 1) or the item is refused.
- Lookup keys: `MEM-ASSOC-Y`, `MEM-FULLNS-Y`, `MEM-FULLS-Y` (each £55 a year, a yearly subscription, kept as separate prices so they can differ later), `MEM-JOIN`, `MEM-BRANCH`, `MEM-BUNDLE`, `MEM-CERT`, `MEM-BADGE`, `MEM-STICKER`. The zero-rated part of every membership fee is £38.00 (the other £17.00 is standard-rated and includes VAT), used only to split net from gross for Creator.
- Monthly payment: see **Monthly plans** below.
- A signed-in user with no CRM Contact may buy (V1 public path): `contact_id` is empty and Creator creates the Contact after payment. A Contact with an active membership must renew or upgrade (`previousId`, owned Deal). **Joining fee** (Guild, 26 October 2026): charged on a new purchase and on a renewal alike, unless the new membership starts no more than one month after the end of the Contact's latest membership of any type (Associate, International, Full Non-Salon or Full Salon; only Active Deals count, a saved draft does not). A membership still running has no gap, so a renewal or upgrade of it pays no joining fee; a gap of more than a month pays it again. A Contact with no earlier membership, or no Contact, pays it. Metadata keys match V1 including net amounts (the zero-rated element of the fee is split out for Creator).
- Page: `/membership/buy` (renew: `?renew=<dealId>`).
- Join page details: the POST also accepts `businessName`, `address1`, `address2`, `town`, `county`, `postcode` (each trimmed to 100 characters). Non-empty values go in the session metadata as `business_name`, `address_line_1`, `address_line_2`, `town`, `county`, `postcode`, so Creator can store the trading name and address. Quotes ignore them.
- Extras are named `Certificate`, `Badge` and `Window sticker` in Stripe line items and the price panel.

## Accreditation: yearly or monthly, renewing
Accreditation is paid yearly or monthly (`billing=annual|monthly`, default annual) and renews automatically either way (agreed with the Guild on 23 October). Yearly: the accreditation line is a yearly subscription line at the live Stripe amount (`ACC-STD`, `ACC-ASSOC`, `ACC-INTL` or `ACC-INTL-MEM`), carrying its code in `metadata.sku`. Monthly: the same plan rules as membership (see Monthly plans), every line `ongoing`, so nothing is charged once and the payment is the same every month; for example £354.00 a year is £29.50 a month plus the £1.50 admin fee, £31.00, and £409.00 is £35.59. Metadata: `subscription_type` (`annual` or `monthly`), `product_amount` (what is charged now: the first payment on a monthly plan) and `product_yearly_amount` (the yearly price either way). An open session is reused only if it was opened for the same plan; a session from before plans (no `subscription_type`) is not reused. Additional venues are still a single payment. The pay page (`/pay/accreditation/:recordId`) has an Annual or Monthly choice.

## Price list codes on Stripe lines
Every Stripe line can be matched to its item in Books by code. Catalogue lines are Stripe prices whose **lookup key** is the code (read it from the line's price). Every **inline** line (insurance premiums and IPT, the named employee fee, an extra branch on a yearly plan, every line of a monthly plan except the admin fee) carries the same code in its product metadata: `line_items[i].price.product.metadata.sku` (expand `data.price.product` on the session's line items). Insurance codes: `INS-MEDMAL-NS`, `INS-MEDMAL-S1|S2|S3`, `INS-EQ-5K|10K|15K|20K` (`-NS` for non-standard construction), `INS-EL-1|3|5`, `INS-TEACH`, `INS-TEACH-PLUS`, `INS-EXT-ELEC|NEEDLE|PIERCE|SPMU|DERMA`, `INS-MONEY`, `INS-NAMED-EMP-NS`, `INS-NAMED-SUB-NS`, `CALC-EL-S`, `CALC-CON`, `CALC-BLD`, `CALC-BI`, `CALC-PA`, and `INS-IPT` for the tax line. The named employee fee carries `MEM-FULLNS-Y` or `MEM-FULLS-Y`. A test checks that every code the portal can send exists in the Books item list.

## Monthly plans
Agreed with the Guild on 21 October (price list version 2); the joining fee and add-ons rule changed on 27 October (MTA-D22). Code: `src/plans.js`; the catalogue marks each line as `ongoing` or `year_one`.
- **The rule.** A monthly plan is the yearly price plus the monthly admin fee, divided by 12, with every payment rounded up to the next penny. What renews (membership, extra branches, insurance premiums, IPT and employee fees) is `ongoing` and is divided into 12 payments. The joining fee and the add-ons (bundle, certificate, badge, sticker) are `year_one`: they are **not** divided; they are charged once, in full, with the first payment. The admin fee is the catalogue price `MEM-ADMIN` (£1.50 a month, £15 plus VAT a year).
- **The payments.** ongoing payment = ceil(ongoing total / 12) plus the admin fee; first payment = ongoing payment plus the joining fee and add-ons in full. Every later payment, including every renewal, is the ongoing payment, so the amount never changes after the first. The pence are shared out so the ongoing lines add up to the payment exactly. Examples: Associate renewal £6.09; Associate new member £16.09 then £6.09 (the £10 joining fee in full); Associate renewal with a badge £10.09 then £6.09; non-salon renewal £9.12; salon (lowest band) £13.09; standard accreditation £31.00.
- **Stripe.** Subscription mode. Each ongoing line is an inline monthly price (`price_data.recurring`), the admin fee is the catalogue price, and the joining fee and add-ons are one-off catalogue prices (no `recurring`) on the first invoice, as on a yearly plan. The subscription carries `plan=monthly` and `contact_id` in its own metadata. `total_amount` in the session metadata is the first payment; for the one-off items the per-item amounts (`joining_fee_amount`, `badge_amount` and so on) are the **full** amounts, while for the lines that renew they are monthly shares (the net splits the zero-rated part as £38 divided by 12); the insurance amounts stay yearly. `monthly_plan` (JSON: payments, first and later payment, `one_off_total`, `year_one_total`, admin fee) is added while there is room under Stripe's 50 key limit.
- **No schedule.** There is nothing that stops after 12 payments, so a monthly plan needs no subscription schedule. The earlier `ensureSchedule` step, the `POST /portal/checkout/finish` call, the portal's own `/stripe/webhook` endpoint and the `phase` and `phased` metadata are gone. (A subscription created before this change may still have a schedule in Stripe test mode; nothing in the portal reads it.)
- **For Creator.** Per-item amounts and invoice lines for membership and insurance are monthly shares and the one-off items are full amounts on the first invoice; the amount charged each month is the same at every payment, including renewals; a subscription's invoices (`invoice.paid`) repeat monthly. Insurance lines are monthly shares of the yearly premium, so the policy amounts in the CRM stay yearly.

## Membership changes (MTA R2, off by default)
`service=membership_change`, `recordId=<membership Deal>`, optional `branches` (comma separated keys) and `addons` (as for add-ons). A one-off payment (`mode=payment`), no GBP 5 fee: the Guild charges the fee for insurance changes (re-issued documents), not for branches or items. Switched on with `PORTAL_MEMBERSHIP_CHANGES_ENABLED=true` (client `VITE_PORTAL_MEMBERSHIP_CHANGES=true`); off, the service, its quote and `GET /portal/checkout/membership-options` answer 503. It stays off until Creator handles the `membership_change` payment, because nothing else acts on it.
- **Who and when:** the Deal must be the signed-in Contact's, Active, started and not expired (409 `MEMBERSHIP_NOT_CURRENT` otherwise, 404 if it is not theirs). A branch the membership already holds (the main one, or an extra already bought) is refused. Up to three extra branches.
- **Extra branch:** the live yearly price (`MEM-BRANCH`) for the days left in the term, from today, both end days counted, over the days the term runs (365, or 366 if it spans 29 February; `src/prorata.js`, the Guild's rule of 26 October), rounded to the penny, one inline line per branch carrying `MEM-BRANCH`. Under 50p is refused (422 `TOO_LATE_TO_CHANGE`).
- **Flat items:** bundle, certificate, badge, sticker at the live catalogue price, in full (not pro-rated), one-off catalogue lines. For a monthly payer they are paid at once.
- **Metadata:** `type=membership_change`, `change_type=mta`, `mta_scope=membership`, `effective_date`, `prorata_days`, `prorata_total_days`, `secondary_branches`, `branch_addon_amount` (and `_net`), `branch_yearly_amount` (what the branches cost from the next renewal), the add-on amounts as for `membership`, and `total_amount` (and `_net`). See [stripe-metadata.md](stripe-metadata.md).
- **Not done here (MTA-D20, D21):** adding the branch to the member's renewing subscription, and a monthly payer's one-off for the billing month with a higher payment from the next. Creator (or a later portal step) acts on `branch_yearly_amount`. Until then a monthly payer who buys a branch is charged the days left in the term now.
- `GET /portal/checkout/membership-options?recordId=` returns each branch and whether the membership already holds it, for the page.

## Insurance changes: quote only (MTA R3-1, off by default)
`POST /portal/checkout/quote` with `service=insurance_change`, `recordId=<membership Deal>` and a `change` object: `effectiveDate`, `addPeople` (`type`, `firstName`, `lastName`), `removePeople` (Insured_People ids), `treatments` (ids), `teaching` (`standard` or `additional`), `equipmentTier`, `elTier`, and the repeated declarations and confirmations. Switched on with `PORTAL_INSURANCE_CHANGES_ENABLED=true`; off, it answers 503. **It only quotes.** Nothing is written to the CRM or Stripe, and `POST /portal/checkout` for this service answers 503 `PAYMENT_NOT_AVAILABLE` until the revision records and Creator are ready (verification gate in `docs/delivery/mta-r3-plan.md`). `payable` is always `false`. Code: `src/insuranceChange.js` (pure), the `insurance_change` entry in `catalogue.js`, and the cover read in `cover.js`.
- **Slice:** Non-Salon policies with `Payment_Frequency = Annual`. Add or swap people, add treatments, teaching, equipment (a verified increase) or Employers' Liability. A Salon policy, a monthly or unknown plan, a removal, a refund, a downgrade, more than four people, new equipment (premises details not collected yet), or a current level that cannot be verified (a blank `Sum_Insured` on equipment; any held Employers' Liability cover, whose `Cover_Option` picklist has no real tiers yet) is `REFER`: `blocked` with the reasons and no lines, so the member is told to call the office. The request is saved for the office when R3-2 adds the revision records.
- **Dates:** from today up to 30 days ahead, never after the policy end, no back-dating (422 with the allowed range). A change in the last 30 days of a policy that is already renewed is `REFER` (MTA-D23): either a later Insurance_Policy in force on the same membership (reported by the cover read as `insurance.renewal`; the current policy is the one covering today, not the latest started) or an Active membership starting after the policy end. The member is told the office will make the change, and can save the request, which is stored as Under Review. Nothing is applied to both terms automatically.
- **Pricing:** the same rating as a new quote (`calculateQuote`), pro-rated by `prorata.js` (days remaining over days on the policy, both end days counted); premium to the penny, then IPT at 12% once on the net. An increase credits what was recorded as paid for the old row (`Premium_Net`) for the days left, not today's table. A like-for-like swap carries the membership fee over; an added employee pays the pro-rated membership fee at the live price; every online change carries the GBP 5 `FEE-MTA` line (a Stripe price with that lookup key must exist, otherwise 409 `ITEM_NOT_AVAILABLE`). All lines are positive; a credit is taken off the item it belongs to.
- **Checks:** the rules (`evaluateRules`) run on the policy as it will be after the change, with the repeated declarations; added names go through the sanctions check.
- **Response:** the usual quote (`lines`, `totalPence`, `payable`, `blocked`) plus `details`: `quoteId` (`QC-` and 16 hex characters, the same for the same cover and change on the same day, so a later payment can be checked against it), `outcome`, `effectiveDate`, `term`, `items`, `premiumNetPence`, `iptPence`, `needsDeclarations`.

## Insurance changes: saving a revision (MTA R3-2, off by default)
`POST /portal/checkout/insurance-change/revision` with the same body as the quote (`service` is set by the route). Needs `PORTAL_INSURANCE_CHANGES_ENABLED` **and** `PORTAL_INSURANCE_CHANGES_WRITES=true`; otherwise 503 and nothing is written. Code: `src/insuranceRevisions.js`. It charges nothing and takes no payment.
- **A payable change** (outcome PASS, every declaration and confirmation answered, else 422 `INCOMPLETE`) is saved as a `Policy_Revisions` record with `Revision_Status = Quoted`: `Policy`, `Membership`, `Change_Type = MTA`, `Change_Scope = Policy Only`, `Requested_Effective_Date`, `After_Quote_ID` (the quote id), `Premium_Delta_Net`, `IPT_Delta`, `VAT_Delta` (the VAT in the GBP 5 fee and the employee membership fee), `MTA_Fee`, `Fee_Waived = false` and `Request_Details`. Then, for each item, a **draft** `Insurance_Extension` (`Status = Draft`, `Policy_Revision`, `Effective_From` the start date, `Effective_To` the policy end, `Supersedes_Extension` = the row an increase or swap replaces, `Sum_Insured` for equipment, `Insured_Person` for a person) and, for each added person, a draft `Insured_People` row (same revision and dates).
- **A referred change** (REFER or STOP) is saved as `Under Review` with the full request in `Request_Details` (the cleaned change including the repeated declarations and confirmations, the reasons, and any people to remove), no amounts and no rows, so the office can pick it up without asking again.
- **Live cover is never edited.** Every record written is new. Creator ends the replaced rows and the removed people when it applies the revision after verified payment. The portal only sets `Quoted` and `Under Review`; `Awaiting Payment` comes with the checkout (R3-3); `Approved`, `Scheduled` and `Applied` are Creator's. If a draft row cannot be written the revision is set to `Withdrawn` and the call answers 502.
- **Ending cover is recorded, not done:** the new rows run from the start date to the policy end, and `Request_Details.endings` lists each replaced `Insurance_Extension` and each removed `Insured_People` row with `effectiveTo` = the day before the new cover starts, so cover is continuous with no overlap and both end days count, the same as the pro-rata. Creator sets those `Effective_To` dates when it applies the revision after verified payment. The portal never edits a live row.
- **Employers' Liability:** adding it where none is held can be saved; any change to held Employers' Liability goes to the office (`EL_OFFICE`) until the pricing tiers are mapped to `Cover_Option`.
- **Repeats:** the same quote id on the policy returns the open revision (200, `reused: true`) and writes nothing. A revision already `Awaiting Payment`, `Approved` or `Scheduled` on the policy blocks a new one (409 `REVISION_IN_PROGRESS`).
- **CRM fields that must exist before the writes switch is turned on** (the first group already exist in the live CRM, per the review of 27 October; the second are new): existing, `Policy_Revisions` (`Revision_Status`, `Change_Type`, `Change_Scope`, `Requested_Effective_Date`, `After_Quote_ID`, `Premium_Delta_Net`, `VAT_Delta`, `IPT_Delta`, `MTA_Fee`, `Fee_Waived`, the `Policy` and `Membership` lookups) and `Insurance_Extension` (`Policy_Revision`, `Effective_From`, `Effective_To`, `Supersedes_Extension`, `Sum_Insured`, `Insured_Person`, `Status`); **new**, `Policy_Revisions.Request_Details` (multi-line text, up to 32,000 characters, the request as JSON), `Policy_Revisions.Stripe_Checkout_Session_ID` (single line text, used from R3-3), and on `Insured_People`: `Policy_Revision` (lookup to Policy_Revisions), `Effective_From` and `Effective_To` (dates). `Policy_Revisions.Name` is mandatory text (120 characters, not auto-numbered), so every revision is named the prefix, a space and its quote id (`PORTAL_REVISION_NAME_PREFIX`, default `MTA`, for example `MTA QC-3F9A...`); a request with no quote id would get a random `REQ-` reference. A referred request is named the same way, before anything is priced.
- The cover read (`GET /portal/records/membership/:id/cover`) lists these revisions with their `status` in the change history.

## Insurance changes: payment (MTA R3-3, off by default)
`POST /portal/checkout` with `service=insurance_change`, `recordId=<membership Deal>` and either `change` (one) or `changes` (a basket of up to three start dates; changes with the same start date are merged into one). Needs `PORTAL_INSURANCE_CHANGES_ENABLED`, `PORTAL_INSURANCE_CHANGES_WRITES` **and** `PORTAL_INSURANCE_CHANGES_PAYMENT`; otherwise 503 `PAYMENT_NOT_AVAILABLE` and nothing is written. The quote shows `payable: true` only with all three on.
- **One revision for each start date, one checkout for the basket.** The revisions are priced in date order, each against the cover as it will be after the earlier ones (a later change can upgrade cover an earlier one adds, and credits it by its annual equivalent). Each revision carries its own `FEE-MTA` line (GBP 5, named with its start date), its own IPT line and, for added employees, the pro-rated membership fee. All lines are inline `price_data` in a single one-off Stripe session (`mode=payment`) that expires after 23 hours 50 minutes.
- **Order of events:** the revisions and their draft rows are saved (as for `/insurance-change/revision`, `Revision_Status = Quoted`), the session is created, then every revision is set to `Awaiting Payment` with `Stripe_Checkout_Session_ID`. If the CRM update fails the session is expired and the call answers 502, so no one can pay for a change the CRM does not know is waiting. If saving a row fails the revision is `Withdrawn` and nothing reaches Stripe.
- **Repeat and resume:** a basket whose revisions are all `Awaiting Payment` on one open session returns that session (200, `reused: true`); paid returns `alreadyPaid`. An identical request within 5 minutes reuses the session. A different change already in flight on the policy blocks a new one (409 `REVISION_IN_PROGRESS`).
- **A referred or incomplete basket is not paid for** (422 `REFERRAL_REQUIRED` or the missing answers): the member removes the change or the office takes it (save it with `/insurance-change/revision`).
- **Metadata** (`type=insurance_change`, see [stripe-metadata.md](stripe-metadata.md)): `membership_deal_id`, `insurance_policy_id`, `change_type=mta`, `mta_scope=policy`, `revision_count`, `revision_ids`, `effective_dates` and `quote_ids` (comma separated, in the same order, up to three), `insurance_amount` (premium and IPT, gross), `insurance_net_amount`, `insurance_ipt_amount`, `mta_fee_amount`, `named_employee_membership` (JSON `{count, amount, amount_net}` or empty), `total_amount`, `total_amount_net`. Creator applies each revision once, keyed on its id, ends the rows in `Request_Details.endings` (and the rows named by `Supersedes_Extension`), and schedules a future start date. Its handler is not built yet, so payment stays off.
- **Needs before it can be switched on:** the writes switch's CRM fields and automation check, a Stripe price with lookup key `FEE-MTA` (GBP 5, including VAT, one-off), and the Creator handler.

## Insurance changes: the member screens (MTA R3-4, off by default)
Client switch `VITE_PORTAL_INSURANCE_CHANGES=true` (also needs `VITE_PORTAL_BILLING` and `VITE_PORTAL_RECORDS`). The function's switches decide what actually works: quotes need `PORTAL_INSURANCE_CHANGES_ENABLED`, saving a request needs `..._WRITES`, paying needs `..._PAYMENT` as well.
- **Entry:** on Your cover (membership management), a **Make changes to my insurance** button for a Non-Salon policy paid yearly. Anything else shows the office number. Route `/membership/manage/:id/changes/new` (`src/InsuranceChange.jsx`, form logic and tests in `src/insuranceChangeForm.js`).
- **Choose:** the current cover is read (`getMembershipCover`) and drives what is offered: people (replace a listed person, add up to four in total), treatments not already held, teaching (standard, or an upgrade to additional), a raise of a verified equipment level, and Employers' Liability where none is held. New equipment, a held Employers' Liability level, removals and anything unverifiable say to call the office. One start date for a change (today to 30 days ahead, never after the policy end); **Add a change from a different date** for up to three, each its own revision and GBP 5 fee.
- **Declarations:** the same statements, treatment questions (when a treatment is chosen), confirmations and demands and needs wording as when the member joined (`INSURANCE_STEPS`), repeated for every change.
- **Review:** the function prices the whole basket (`POST /portal/checkout/quote`, `changes`), showing each line, the days left for each start date and the total. A basket the function refers shows the reasons and **Save my request for the office** (`/insurance-change/revision`) with a reference, so the member does not start again. If payment is not switched on the same save is offered. Pay opens Stripe Checkout (`POST /portal/checkout`), then the usual payment return page.
- **Status:** the change history tab lists each revision with its status (Quoted, Under Review, Awaiting Payment, Approved, Scheduled, Applied, Withdrawn).
- Not viewed in a browser against live data; the screens render from sample cover in a server-side check.

## Adding a service
1. Add its items to `ITEMS` and create the Stripe price with the matching lookup key (the Books item's SKU).
2. Add an entry to `SERVICES` with `prepare()` (ownership check, lines, metadata).
3. Add a route link in the portal to `/pay/<service>/<recordId>`.

## Env
`PORTAL_BILLING_ENABLED=true`, `STRIPE_SECRET_KEY` (test), `PORTAL_PUBLIC_ORIGIN`. No price IDs: prices are found by lookup key. Client: `VITE_PORTAL_BILLING=true`. Not sent: the Stripe webhook secret.

## School referral code
Off unless `PORTAL_DISCOUNTS_ENABLED=true`. Plan: `docs/delivery/vouchers-review.md`, phases 0 and 1. Test mode only.
- **Joining fee.** Whether it is due is the existing rule (`joiningFeeDue` in `catalogue.js`): new, or a gap of more than a month since the last membership ended. The code only applies where a fee is due.
- **Code.** The code is the school's **Accreditation Reference** (`ACC - 0140`; `ACC-0140` and `acc 0140` are the same). The quote and checkout accept `code` on `service=membership`. It is looked up on `Training_Centre_Accred` on `Name` (override with `PORTAL_DISCOUNT_REFERENCE_FIELD`; empty switches codes off). It counts when the `Accreditation_Status` shows the accreditation was issued (Verified, Expired, Closed, Suspended, Revoked), so an expired school still gives the £10; drafts and rejected applications do not. One message, "That code is not valid", and about 10 different wrong codes an hour per person (then HTTP 429). A code is ignored with a message when no joining fee is due.
- **Pricing.** A valid code leaves the joining fee line out before `plans.splitMonthly`, so yearly and monthly are exact (monthly Associate first payment £6.09 with the code, £16.09 without it, since the first payment carries the joining fee in full). The quote returns `joiningFee {due, amountPence}`, `discount {code, label, amountPence, line, lineName, indicative}` and `codeResult {status, message}`.
- **Guests.** A guest quote is indicative: the code is only checked for shape and nothing is recorded. It is checked against the CRM once the customer is signed in.
- **Recording.** Redemptions live in Creator. The portal writes nothing for a redemption: Creator records it from the one `discounts` metadata key (see `stripe-metadata.md`).

## Insurance
Ported from V1 (`calculateInsuranceQuote`, `evaluateInsuranceRules`, `createInsuranceRecords`) into `src/insurance.js`. Two entry points: `service=insurance` (standalone, now a yearly subscription so the insurance renews) and `service=membership` with an `insurance` object (membership subscription plus insurance in one checkout, metadata `type=membership_insurance`).
- **Request**: `country` (territory) and `insurance` (the V1 `ins*` answers). The body is cleaned to a fixed shape: unknown keys are dropped, numbers are bounded, at most 10 named people, and the route is derived from `insSalon`, never trusted from the browser. Use `POST /portal/checkout/quote` (the answers are too big for a query string); `GET /quote` still serves the other services.
- **Rating**: V1 tables and formulas. Premiums are computed, so each cover row and the IPT line (12% of the net total, rounded once to the penny) go to Stripe as inline `price_data` (name, `unit_amount`), not catalogue price IDs. Insurance renews automatically (agreed with the Guild): the cover rows, the IPT line and the employee membership fees are yearly subscription lines (`price_data.recurring.interval=year`), alongside the membership when bought together, and `subscription_data.metadata.plan=annual`. The renewal charges the same amounts as the first year: premiums are not re-rated at renewal, and the renewal date is a year after payment, not after the chosen policy start date (up to 30 days apart).
- **Named people** (price list version 2, agreed 21 October): a non-salon employee pays the £32.50 premium (IPT on top) and a £55.00 membership fee; a non-salon subcontractor pays the £15 premium; a salon employee pays the membership fee only, with no premium or IPT; a salon subcontractor pays nothing. The membership fee is one inline line per employee group (`Named employee membership fee`, quantity = employees) charged once at the live Stripe price (`MEM-FULLNS-Y` non-salon, `MEM-FULLS-Y` salon). It carries VAT (the £38 zero-rated split applies), so it is outside IPT and `insurance_amount`. Metadata `named_employee_membership` is JSON `{count, amount, amount_net}` (one key: Stripe allows 50) and `total_amount` includes the fees. More than four people is still a REFER.
- **Treatment extensions**: advanced electrolysis is £30.00 before IPT (£33.60). **Property away**: the £10,000 single-item limit is wording in the journey, no longer a question or a check; the £25,000 total limit still stops the quote.
- **Rules** (STOP, REFER, PASS): as V1. Territory is UK, the UK nations, Channel Islands or Isle of Man (V1 treated "England" and the other nations as unsupported; the portal's country list contains them, so they count as UK here). Paying also requires every declaration and confirmation to be answered (V1 left that to its wizard), and the premises address when property cover is chosen.
- **Not payable online**: a REFER or STOP quote is returned by `/quote` with `payable: false` and the reasons, and `POST /portal/checkout` refuses it (422, `REFERRAL_REQUIRED`) before anything reaches Stripe. A pay attempt that is REFER or STOP is recorded in the CRM for the Insurance team (a `Referred` Insurance_Policy, see [insurance-risk-checks.md](insurance-risk-checks.md)); a quote never writes anything. Once recorded, the 422 body also carries `details: {reference, status}`: `reference` is the Insurance_Policy record id and `status` is `Referred` or `Stopped`. The message text is unchanged and never says why. An INCOMPLETE answer records nothing and has no `details`. The portal replaces the error with a confirmation panel showing the reference, keeps the customer's answers and does not offer Pay again for the same answers. The sanctions, flood and subsidence checks add their findings to these rules.
- **CRM records before payment, as V1**: Insurance_Policy (Application_Status `Ready for Payment`, Entry_Route `Existing Member` or `Public Prospect`, Membership = the current active Deal if any), Insured_Premises, Insured_People, Insurance_Extension (one per cover row) and Declarations. Created only on a payable checkout, never on a quote. Their ids go in the session metadata exactly as V1: `insurance_policy_id`, `insured_premises_id`, `insured_people_ids`, `insurance_extension_ids`, `insurance_declarations_id`, plus `insurance_amount` (gross), `insurance_net_amount`, `insurance_ipt_amount`, `insurance_route`, `insurance_requested`. For membership with insurance `total_amount_net` adds the insurance total, which carries no VAT.
- **Cover levels and payment frequency saved** (MTA R3, from the live CRM review of 27 October): the policy gets `Payment_Frequency` (`Annual`, or `Monthly` when the membership is bought on a monthly plan) and, for a Salon with Employers' Liability, `Annual_Wage_Roll` (`Annual_Turnover` was already saved). Each cover row gets `Sum_Insured` where the member chose a level: the Non-Salon equipment tier, and for a Salon the total of the headings under Contents, Buildings, Business Interruption and Property Away. Liability, treatments, people and Money have none. A Non-Salon Employers' Liability tier is not saved yet: `Cover_Option`'s type and values are still to be confirmed. A later change reads these to offer only a real increase, and sends anything it cannot verify to the office.
- **Standalone metadata**: `type=insurance`, `quote_reference`, `entry_point`, `contact_id`, `membership_deal_id`, `membership_profile_id`, `name`, the insurance keys above, `total_amount`. V1 had no standalone insurance checkout, so Creator's webhook needs a branch for `type=insurance` (activate the policy from `insurance_policy_id`).
- **Contact link**: same rule as membership. A verified email matching one Contact is linked; no Contact means a public prospect (`contact_id` empty, Policy and Declarations have no Contact) and Creator creates the Contact after payment.
- **Property cover needs Contents** (Guild, 26 October 2026): Money, Buildings, Business Interruption and Property Away are only offered to a Salon applicant who has chosen Contents cover. The buy form hides those sections until Contents is yes, taking Contents off the quote takes them off too, and `clean()` drops any of the four sent without `insContents`, so they are never rated or recorded.
- **Who may buy**: insurance is included with Full membership only. Standalone insurance needs a current Full membership (Active, in date, Full Member (Non-Salon) or (Salon)); membership with insurance is refused for the Associate level. Both return 409 `INSURANCE_NEEDS_FULL_MEMBERSHIP` with a customer message.
- **Retries**: an identical application (same answers, lines and user) within 5 minutes reuses the CRM records and the open Stripe session, so a double click or retry creates one set of records and one session. Per function instance, like the rate limiters. A failed attempt is forgotten so the retry can succeed.
- **Limits**: pay attempts that create insurance records are limited to 3 a minute and 10 an hour per user (429 `RATE_LIMIT`); a reused attempt does not count. Quotes keep the general limit.
- **Known limit**: a payment abandoned for more than 5 minutes leaves the policy at `Ready for Payment`, and a new attempt creates a new set of records. Creator can expire stale ones.
- **UAT changes to the answers (AL-INS log, rows 004 to 075)**: the rating tables and prices are unchanged; only what the portal collects and some rule wording moved.
  - Turnover is three radio bands (up to £100,000, £100,001 to £175,000, £175,001 to £250,000). The portal sends the band's upper limit as `insTurnover`, which falls on the same £75, £100 and £150 medical malpractice bands as before. Above £250,000 is a STOP as before (the portal gives the office number instead of an option).
  - Wage roll is a yes/no, `insWageRollOver125k` (salon only). `yes` is a STOP (`WAGE_ROLL_LIMIT`, "Please call the office to discuss your application."). The wage roll figure `insWageRoll` is only asked when Employers' Liability is added, still rated at 0.2%, minimum £75, and a figure over £125,000 is the same STOP.
  - `insPropertyAwayMaxItem` (salon, property away): the highest single item. Over £10,000 is a STOP (`PROPERTY_AWAY_ITEM_LIMIT`). It is not stored in the CRM yet (no field).
  - Declarations are shown as statements ("I agree" or "I do not agree"). The portal turns each answer into the answer the function expects before sending `insDeclarations` (agreeing is `no` for the first five and `yes` for the last two), so the request, the REFER rule and the Declarations record are unchanged.
  - Treatment extension names (quote lines, `Cover_Summary`) now read as the customer's list: "Red Veins, Skin Tags, Milia, Warts & Moles by Advanced Electrolysis", "Microneedling or Dermarolling", "Nose and Cartilage Piercing", "Microblading, Semi-Permanent Make Up & Micropigmentation", "Dermaplaning".   - The buy page has one section per cover, no running price panel, and a quote summary where each cover can be edited or removed (the portal maps a quote line back to its answers by its name, `Insurance - <label>`). - Pages: `/insurance/buy` and the "Add insurance" section of `/membership/buy`. The questions live in `src/insuranceInputs.js` and also drive the saved-application journey.

## Start dates
- Membership and insurance take an optional `start` (ISO date). No date means today. A date from today up to 30 days ahead (UTC days, `START_WINDOW_DAYS` in `catalogue.js`) is accepted; anything else is refused with 422 and the allowed range, never silently changed.
- A membership bought with insurance uses one date for both. The term and the policy year each end the day before the anniversary.
- The date goes to Creator as `membership_start` and `membership_expiry`, and for insurance as `insurance_start_date` and `insurance_end_date`. The insurance policy record is created with `Policy_Start_Date` and `Policy_End_Date`.
- The member pays now. The portal shows any record whose start date is after today as Coming soon with the date, until that day.
- Whether Creator and the CRM treat a future-dated record as pending until its start date is Creator's side to confirm.

## Guest pricing (no account)
- `POST /public/quote` prices a **membership** (optionally with insurance) for a signed-out visitor, so the buy form can be filled in and priced before sign-up. It is off unless `PUBLIC_QUOTES_ENABLED=true` (and billing is on); the client flag is `VITE_PORTAL_PUBLIC_QUOTES`.
- It reads only Stripe prices and the rating tables. No CRM, Creator or Analytics call is made, there is no risk screening, and no record is written. The answer is marked `indicative: true`: the real checks (including sanctions, flood and subsidence) run when the member pays.
- Renewals, upgrades, standalone insurance and accreditation are refused (422 `SIGN_IN_FOR_PRICE`). Rate limited to 30 a minute per client.
- Checkout, drafts and every record write still need a signed-in account. The buy page keeps a guest's answers in the browser tab (sessionStorage, never sent anywhere, consent never restored) and sends them to the account checkpoint at the Pay step; the answers are cleared after a successful payment.

## International accreditation

A centre outside the UK is flat-rated and VAT-free (V1): £350, or £405 with the £55 International membership when the applicant has no current membership. Items `accreditation_international` (`STRIPE_PRICE_ACCREDITATION_INTERNATIONAL`) and `accreditation_international_bundle` (`STRIPE_PRICE_ACCREDITATION_INTERNATIONAL_BUNDLE`) hold the Stripe price IDs. Until both are set the checkout answers 409 "cannot be bought online yet". The metadata membership type is International.

### Resuming and expiring insurance quotes
- Each payable attempt stores on the Insurance_Policy `Stripe_Checkout_Session_ID`, `Quoted_Amount` (gross, with IPT) and `Quote_Expiry` (date). The Stripe session is created with `expires_at` 23 hours 50 minutes ahead (Stripe's maximum is 24 hours), and `Quote_Expiry` is that day.
- `POST /portal/checkout/resume {policyId}` (own Contact's policy only, status `Ready for Payment`): an open session returns its `checkoutUrl`; a paid one returns `alreadyPaid`; an expired, missing or never-created session sets `Application_Status = Expired` and returns 409 `QUOTE_EXPIRED`. Referred and Stopped quotes are not resumable (and stay hidden from the member).
- Records: insurance records carry `quotedAmount`, `quoteExpiry` and `canPay`. A `Ready for Payment` policy past its `Quote_Expiry` shows as Expired without a CRM write. The record page shows the quoted amount and a "Pay now" button when `canPay`, or "Get a new quote" when expired. Creator's webhook should still set the status on payment.

## Contact for a new customer

A signed-in customer with no CRM Contact gets one when they press Pay, or when their insurance quote is referred or stopped and recorded, so the policy, the referral and the payment all belong to a person in the CRM. Only the verified Catalyst email finds or makes the Contact (never a browser-supplied id); the first name, surname and any address typed on the page only fill in a new Contact. A price check, an incomplete form, or a purchase the rules refuse (for example standalone insurance without a Full membership) makes none. A Contact made at checkout is still treated as a new prospect: `entry_point` stays `public` and the policy `Entry_Route` stays `Public Prospect`, and the payment now carries `contact_id` and `client_reference_id`. CRM search can lag a Contact made moments ago, so one made by this function is confirmed by id and exact email, never made twice.

## Upgrade from Associate to Full, with the unused Associate fee credited

Added 29 October 2026, behind `PORTAL_MEMBERSHIP_UPGRADE_ENABLED` (off by default). **Off, an upgrade (`changeType=upgrade` with `previousId`) is priced exactly as before: the full Full price, no credit.** On, and for staff through `POST /staff/quote` and `POST /staff/payment-link` (they share the same pricing):

- **Eligibility.** The membership being upgraded must be the Contact's own, **Active**, an **Associate** membership, with its payment found in Stripe (the paid subscription checkout whose `membership_start` and `membership_expiry` match the Deal's dates). **Yearly or monthly payers are supported** (a monthly payer's credit is limited to the instalments actually paid: see below). The new membership must be **Full with insurance**. Anything else is refused with `422 UPGRADE_NOT_AVAILABLE` and "Please call the office to upgrade": the member is never silently charged the full price. An upgrade cannot yet be combined with the additional branch discount.
- **The credit** is the unused part of the Associate **membership fee actually paid** (not the joining fee, admin fee or add-ons): `fee paid - ceil(fee x used days / term days)`, which is the fee x unused days / term days rounded down, never below zero. Days run from the upgrade date (the new start, up to 30 days ahead) to the Associate end date. Example: £55.00, 275 of 365 days left: **£41.43**.
- **A monthly Associate.** The year's fee is twelve times the monthly share; the value used is rounded up as above; the credit is `max(0, shares paid so far - value used)`, so a member who has paid little more than they have used gets little or nothing. Example: shares of £4.59, 4 paid (£18.36), 90 of 365 days used (valued at £13.59 of the £55.08 year): **£4.77**.
- **The net.** The credit comes off what is charged now (the first payment on a monthly plan), capped at it, so it is never paid out. The new Full term is not pro-rated (start + 364 days).
- **The quote** gains an `upgrade` object: `{ creditPence, appliedPence, netPence, unusedDays, termDays, associateEnds }`, and `totalPence` is already the net.
- **Stripe.** The credit is one `amount_off` coupon (`once`, one redemption, "Associate membership credit") on the Checkout Session; the Associate fee is credited, **not refunded in cash**.
- **Metadata** (`membership_insurance` only, optional): `upgrade_credit` (GBP, gross) and `previous_subscription_id` (the Associate's Stripe subscription, which **Creator ends at `membership_start`** once the payment is verified). See [stripe-metadata.md](stripe-metadata.md).

## Combined membership flow: answers instead of a level

Behind `PORTAL_COMBINED_FLOW_ENABLED` (off by default; the switch is in `scripts/deploy-functions.sh`'s allow list). Design: `docs/delivery/combined-membership-flow-spec.md`.

With the switch on, `service=membership` on every customer and staff route (quote, pay, staff quote and payment link) takes `answers: { country, insuranceRequired, working }` and **no `level`**. The server decides the level with `decideMembership` (`src/membershipDecision.js`) and returns it in `quote.decision`:

```json
{ "level": "full_non_salon", "insurance": true, "route": "non_salon", "steps": ["about_you", "how_you_work", "..."], "message": null }
```

| Answers | Level |
|---|---|
| `country` outside the UK, England, Scotland, Wales, Northern Ireland (the Channel Islands, the Isle of Man, Ireland and Other included) | `international`, no insurance, `message` set, yearly only |
| UK, `insuranceRequired` no | `associate`, no insurance (any insurance details sent are dropped) |
| UK, yes, `working` one of `insWorkingFromHome`, `insMobile`, `insRentedRoom`, `insSubcontractor` | `full_non_salon` with insurance |
| UK, yes, `working` `insSalon` | `full_salon` with insurance |

Refusals (all 422): `LEVEL_NOT_CHOSEN_BY_CLIENT` (a `level` was sent), `MISSING_ANSWER`, `INVALID_WORKING` (more than one answer, an unknown one, or insurance flags that disagree with `working`), `COUNTRY_MISMATCH` (a separate `country` differs from the answers), `BILLING_NOT_AVAILABLE` (monthly for International). Upgrades still go through the existing upgrade check, which refuses a non-Full level. With the switch off nothing changes: a `level` is sent and `answers` is ignored.

`membership_level` in the Stripe metadata may now be `international` (price `MEM-INTL-Y`, £55.00 with £38.00 zero-rated).
