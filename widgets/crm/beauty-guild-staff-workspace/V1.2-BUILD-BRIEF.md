## 0. Hosting and deployment architecture (revised 24 October 2026)

The Staff Workspace frontend is **externally hosted on Catalyst Slate** and registered in Zoho CRM as an external-hosted **Web Tab widget** using the fixed HTTPS Slate URL. CRM metadata, records and staff CRM SDK context remain in Zoho CRM. Pricing, underwriting and screening stay in the **existing** `beauty_guild_api` Catalyst backend. Frontend and backend deployments are independent.

The initial Slate deployment is the runnable V1.1 static widget, with a root `index.html`; the planned V1.2 rebuild is **not** yet implemented. Current Slate Git inputs are documented in [SLATE-DEPLOYMENT.md](SLATE-DEPLOYMENT.md). This branch includes a snapshot of the latest Portal `main` at branch creation and the V1.1 widget source; refresh/rebase against newer Portal changes before application parity is signed off.

Do not embed privileged Catalyst API credentials in Slate static files. CRM-side functions/Connections and staff authorisation must be verified before enabling internal sanctions evidence or risk decisions. Confirm iframe policies, cross-origin configuration, and CDN caching in actual CRM Development. Updating the Slate deployment does **not** alter the existing Zoho CRM internally hosted widget until the CRM external-hosted widget URL is configured.

## 1. Outcome and principles

Deliver a usable **CRM-first staff workspace**, not a separate customer portal or a set of high-level cards. The experience combines:

1. **Zoho CRM depth:** browse complete accessible datasets, see comprehensive record fields and statuses, work with related records, CRM actions, Notes, Tasks and email.
2. **Portal V2 journeys:** current Membership, Insurance and Accreditation questions, conditional behaviour, explanations, document links, validation and visual language.
3. **Single CRM source of truth:** selected Contact, related application records, persistent save/resume and hand-off between an authorised staff user and the authenticated customer.
4. **Existing Catalyst calculation/checking logic:** authoritative pricing, underwriting, sanctions, flood/subsidence; internal reasons and audit evidence, with no second pricing or risk engine.
5. **Payment boundary:** show a real, verified quotation and a disabled **Generate payment link / Payment coming next** step until Creator payment-processing integration is ready.

The user-approved design principle is **CRM information depth + Portal V2 styling + staff-focused processing**. Use UK spelling. Clearly distinguish **Implemented**, **Proposed**, **Unavailable** and **Not run** in code, UI and UAT notes.

## 3. Record-list and record-detail design standard

### 3.1 Module lists

Use **tables** with CRM-like headers rather than large individual record cards. Modules expose relevant columns, for example:

- **Insurance:** policy/application reference, insured trading name, Contact, policy type, application status, underwriting, sanctions/risk outcome, payment status, policy status, start/end, assigned owner/next action.
- **Membership:** Contact, Deal/reference, member type, branch, current profile/membership status, Deal stage, payment/renewal status, dates and restrictions.
- **Accreditation:** application/reference, school/Account, applicant Contact, level, stage, verification, payment, validity, next action.
- **Customers:** Contact name, email, phone, membership context, latest activity and linked application counts if legitimately returned.

Tables support selectable rows, configurable/saved columns where feasible, API-side filtering and sorting, reliable next-page loading, explicit total-coverage caveats, and preserved navigation. Optional compact status summaries should **never replace** the record's actual status fields.

### 3.2 Record detail (target layout)

- **Top:** breadcrumb; record name/reference; linked Contact and company; independent status chips; owner/next action and last modified; contextual toolbar.
- **Main:** `Details`, `Timeline`, `Processing` views. Details are grouped like a CRM layout and show readable label/value pairs in a compact two-column grid; optional `All fields` reveals permitted non-core values. Fields from custom lookups hyperlink to the linked record.
- **Right sidebar:** **Related Lists** navigator with per-list label and count if available. Insurance includes Extensions, Insured People, Premises, Declarations, Risk Screenings, Revisions, Notes, Tasks, attachments/documents. Accreditation includes Centres, Course Offerings, Tutors, Qualifications, Extensions and activity; Membership/Contacts use relevant CRM relations.
- **Related list selection:** replace main detail area with a proper table (appropriate columns, filters/pagination and child drill-down) **while keeping parent header and right navigator visible**.
- **Processing:** show applicable CRM buttons/actions, customer restrictions, verification/underwriting information and decision/audit history; use safe native-CRM hand-off for actions not proven callable in-widget.

Related lists must use **verified API names**, not guessed names. Distinguish `0 records`, `Permission denied`, `API not available` and `Not yet loaded`. Do not silently omit a failed related list.

### 3.3 Staff application journey layout

Use Portal V2's actual field components/behaviour with a **persistent CRM customer context** (Contact, current Membership, saved draft, quote and check status) alongside the questionnaire. Keep progress, Save, Back, Continue and Exit visible and usable. Side context can collapse on smaller screens. Preserve document explanatory text and links at the relevant question.

### 5.2 Secure CRM-to-Catalyst access

> **Design and decision (27 October 2026):** [STAFF-API-AND-IDENTITY.md](STAFF-API-AND-IDENTITY.md) turns this section into a build design: signed requests from a CRM-side function, a server-side staff and role check, and API Gateway as a later hardening step, not a dependency.

- Preferred: CRM widget → **CRM-side function/Connection** holding secrets → protected Catalyst staff routes. Do not place shared credentials, Stripe keys or privileged Analytics/Creator tokens in browser-accessible widget code.
- Authenticate the **actual staff identity**, role/permission and CRM record access server-side; verify selected Contact and application linkage, not only a client-supplied ID. Record staff identity separately from the customer's identity.
- Establish API Gateway/Security Rules strategy **without changing existing customer Portal V2 authentication or breaking routes**. Check whether API Gateway is already enabled before changing it. Use least-privilege access and restricted responses for sanctions findings.
- Rate limit and audit repeated assessments; avoid redundant sanctions queries and duplicate `Risk_Screenings`. Preserve the previous assessment when a newer result is stale, incomplete or errored.
- Do not accidentally call `POST /portal/checkout` for quotes: it can create CRM insurance records and a Stripe session. A quote or assessment must remain side-effect-controlled.

## 6. Internal screening result standard

Every applicable check must return/display:

- **Check:** sanctions / flood / subsidence / member gate / underwriting / qualification or declaration eligibility.
- **Outcome:** `PASS`, `REFER`, `STOP`, `INCOMPLETE`, `ERROR`, `NOT_RUN` (and separate manual decision where applicable).
- **Internal explanation:** exact triggering rule code, relevant answer/record attribute (masked where necessary), match/evidence type, data source and version or timestamp, and why it blocks/permits progress.
- **Required action:** continue, request missing information, refer to Insurance Team, investigate potential sanctions match, stop, or retry unavailable checks.
- **Audit:** assessment ID, time, applicable screening data version, related application/Contact and staff actor, with later manual decision/time/reviewer distinguished from the automated outcome.

For sanctions: show authorised staff **potential match evidence**, matched identities/aliases and identifier context for manual investigation; a potential match is **not** a confirmed sanctions hit. Restrict evidence by role and never display more sensitive data than needed for the task. For errors: retain enough operational detail for support, but do not show API credentials, tokens or unfiltered sensitive payloads.

**No silent pass:** a disabled risk feature (`ran:false`), unavailable Analytics or Creator, stale sanctions dataset, missing required input or a failed synchronisation must **not** be labelled Cleared. In particular, a quote being numerically calculated is not equivalent to verified eligibility or safe issuance. Quotes requiring checks must remain non-payable in the staff workflow until required checks are complete and acceptable.

## 7. Shared draft and declaration safeguards

- **One Contact and one linked application/draft** across staff and customer; prevent duplicates using existing CRM keys, safe retry and revision logic. Staff may create a Contact explicitly with a duplicate/email check; selected customer account linkage must be verified.
- Save answers **at any stage**, preserve conditional answers and journey position, show saved time, by whom and source (CRM staff/customer portal). Use revision conflicts rather than overwriting the other channel's changes.
- Membership and Insurance drafts currently use CRM modules/Notes and `Journey_ID`; Accreditation uses the actual Account/Centre/Application/course/tutor related-record model. Implement hand-off without flattening these different models or creating duplicate records.
- Prefill facts only. **Never pre-agree** declarations/terms for the customer. Record whether staff entered each statement and whether the customer actually confirmed it; do not imply a customer personally accepted a term if the evidence is only a staff assertion.
- Apply CRM permissions and ownership before updates, preserve an audit trail, and avoid creating active policies or activating workflows from an unconfirmed application save.

## 8. Delivery sequence

1. **UX foundation:** CRM-style record lists, comprehensive detail page and sidebar related-list navigation, richer Customer 360; preserve existing Notes/Tasks and safe CRM action fallbacks.
2. **Application parity:** replace V1.1's abbreviated `JOURNEY_FLOW` with aligned current Portal V2 forms, reusable definitions, validation, guidance, responsive steps and customer prefill.
3. **Cross-channel drafts:** CRM-backed save/resume for all three services, consistent staff/customer ownership and revision handling, explicit Contact creation where required.
4. **Catalyst staff API:** protected staff identity/context service; actual eligibility and checks with internal evidence and CRM audit history; pricing/quotation results using current price list/Stripe test configuration.
5. **Review/pay boundary:** integrated application review, approved/non-payable outcomes, full quote and recurring breakdown; disabled Generate payment link; comprehensive development UAT.
6. **Later phase (outside V1.2):** enable Stripe link generation and Creator V2 webhook/log/subscription/Books fulfilment, after payment-path UAT and approval.

Build on branch `feature/beauty-guild-staff-workspace-slate`; Git auto-deploy to the designated **Development** Slate app is permitted for testing once configured. Do **not** merge into `main`, replace the live CRM widget or deploy to Production without approval. See [Slate deployment setup](SLATE-DEPLOYMENT.md).
